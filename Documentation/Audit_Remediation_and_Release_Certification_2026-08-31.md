## 1. Purpose and interpretation

This document maps every tracked audit item to the current remediation, source evidence, automated checks, and remaining release-certification work. It does not replace or revise the original audit. The original observations remain the historical baseline.

The words used here have deliberately narrow meanings:

| Status | Meaning |
|---|---|
| Implemented — automated | The remediation is present in source and a focused automated contract exercises the central behavior. |
| Implemented — source/build | The remediation is present and compiles, but the post-fix interaction or accessibility behavior still needs manual certification. |
| Implemented — signed certification pending | The local contract is implemented and generally unit-tested, but production signing, entitlements, an account, a service, or physical hardware is required to certify it. |
| Partially certified | Some layers are verified, but one or more explicitly named acceptance paths remain. |
| Pending | The requested behavior is not yet demonstrated by the repository or available evidence. |

An automated model, persistence, parser, or accessibility-label test is not a substitute for an auditory VoiceOver pass, physical input test, compact-layout inspection, live CloudKit/notification/widget/Spotlight/Shortcut run, or destructive recovery exercise. Accordingly:

- No signed physical-device or production-account path is marked passed in this companion.
- No post-remediation simulator interaction is inferred from a successful compile.
- The release remains conditional until the manual and signed matrices in sections 7 and 8 are completed against the final release candidate.
- Paths and test names identify durable repository evidence. Line numbers are intentionally omitted because the remediation branch is still moving.
